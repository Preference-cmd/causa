## 0.2

**0.2.0** is a minor release with one break, in token usage. The promise of
0.1 carries over: a break of the public Rust API or of the stable serialized
set comes only in a minor release, now `0.2` to `0.3`, and patch releases
fix or add without breaking, so `causa = "0.2"` picks them up. Cargo does not
move a `"0.1"` requirement to `0.2` on its own.

`ModelUsage` reports four counts that do not overlap and mean the same on
every protocol: `input_tokens` (input that neither hit nor was written to
the prompt cache), `cache_read_tokens`, `cache_write_tokens` and
`output_tokens`. A cache count is `None` when the endpoint does not report
it. `reasoning_tokens` is part of `output_tokens`; do not add it to a total.
Causa adds no totals: a host that wants the prompt size adds `input_tokens`
and the two cache counts. On OpenAI Chat Completions and Responses,
`input_tokens` used to include cached tokens; on Anthropic Messages it
already meant uncached input.

Also in 0.2.0: Chat and Responses fill `cache_write_tokens` when the endpoint
reports it, Chat reads a top-level `prompt_cache_hit_tokens`, Anthropic fills
`reasoning_tokens` from `output_tokens_details.thinking_tokens`, and the
`agent.round` span records `usage.input`, `usage.cache_read`,
`usage.cache_write` and `usage.output`. With `CacheDirective::StablePrefix`,
the Anthropic conversation cache breakpoint now lands on the final message
even when it carries this round's tool results, so a fresh tool result is
written to the cache on the request that adds it. The serialized form of
`Context` is unchanged.

## 0.1

**0.1.0** is the first minor release. Its API and the serialized form of
`Context` are those of 0.0.7; what changes is the promise. From 0.1.0, a
break of the public Rust API or of the stable serialized set (`Context` and
every type it contains) comes only in a minor release, `0.1` to `0.2`, with
its migration at the top of the release notes. Patch releases fix or add
without breaking, so `causa = "0.1"` picks them up. Adding an optional field
with a serde default is not a break. Other serializable types, such as model
output, request options, identifiers and error kinds, carry no promise.

On GitHub, a minor release is a regular release and a patch release between
minor releases is marked as a pre-release.

In the earlier `0.0.x` series any release could break, and Cargo does not
upgrade `"0.0.7"` to `0.1.0` on its own.

**0.1.1** is a patch release. It fixes the README's first program and the
`quickstart` example, which did not set the output limit the Anthropic
Messages gateway requires; the API and the serialized form are unchanged.

**0.1.2** is a patch release that adds to the API. Tool processors can read
what each bound tool declares about its effects (`ToolHints`, which the MCP
client fills from a server's tool annotations) and a value the host passes
for the run (`ProcessorData`); see [Process tool
calls](/guides/process-tool-calls/#ask-only-when-it-matters). Existing code
compiles unchanged, and the serialized form is unchanged.

**0.1.3** is a patch release that adds to the API. A host can choose where a
local MCP server's stderr goes with `McpToolSource::connect_stdio_with_stderr`,
so a server's log stays out of a terminal the host draws and its startup
errors can be read; see [Connect MCP
servers](/guides/connect-mcp-servers/). `connect_stdio` is unchanged, and the
serialized form is unchanged.

**0.1.4** is a patch release that adds to the API. A host can send its own
headers to a remote MCP server with
`McpToolSource::connect_http_with_headers`, for a server that asks for an
API key header or another `Authorization` scheme instead of a bearer token;
see [Connect MCP servers](/guides/connect-mcp-servers/). `connect_http` is
unchanged, and the serialized form is unchanged.

**0.1.5** is a patch release that fixes the tool-result contract. A status
now says whether a result was reported: `TimedOut` and `Cancelled` are a
tool's own report and may carry partial output, `Rejected` is a call that
never ran, and `unknown_outcome` is a result nobody observed. The `Tool`
docs state what a turn stop drops and what a tool must finish by its call
deadline, and every synthesized `unknown_outcome` names its cause in
`meta.extra.reason`; see [Write a tool](/guides/write-a-tool/) and [Handle
interrupted runs](/guides/interrupted-runs/). The `McpToolSource::close`
docs describe what its two-second wait covers. The API is unchanged, and the
serialized form is unchanged.

## Upgrading from 0.1

Change the dependency to `causa = "0.2"`; from an earlier 0.1 release, the
sections below need no code changes. Stored contexts load unchanged. Then
check code that reads `ModelUsage::input_tokens`:

| 0.1 usage | 0.2.0 replacement |
| --- | --- |
| `input_tokens` as the prompt size on Chat Completions or Responses | `input_tokens + cache_read_tokens.unwrap_or(0) + cache_write_tokens.unwrap_or(0)` |
| `input_tokens - cache_read_tokens` to get uncached input on those protocols | `input_tokens` |
| `cache_write_tokens` assumed `None` on Chat Completions or Responses | It is `Some` when the endpoint reports cache writes |
| `reasoning_tokens` assumed `None` on Anthropic Messages | It is `Some` when the endpoint reports thinking tokens; it is already counted in `output_tokens` |

Anthropic Messages code that reads `input_tokens` needs no change.

## Upgrading from 0.1.4

Run `cargo update -p causa`; a `causa = "0.1"` dependency already allows
0.1.5. No code changes are needed. Code that matches `meta.extra.reason`
sees `call_deadline_backstop` instead of `call_control_stopped` for a call
whose own deadline had passed before it started, and new reasons for the
other synthesized results. A host that answers calls left pending by an
interrupted run should answer them `Rejected`.

## Upgrading from 0.0.5

Change the dependency to `causa = "0.1"`. The changelog lists every break
with its migration; 0.0.7 and 0.1.0 add none:

| 0.0.5 usage | 0.0.6 replacement |
| --- | --- |
| `MediaPayload::new(media_type, data_base64)` | `MediaPayload::inline(media_type, data_base64)` |
| Reading `payload.data_base64` | Matching `payload.source` (`MediaSource::Inline { data_base64 }`) |
| `with_max_inline_media_bytes(n)` | `with_max_inline_media_bytes(MediaKind::Image, n)`; documents have their own ceiling |
| Expecting a `[tool result media for call …]` user message on Responses | The media inside `function_call_output.output` |

## Upgrading from 0.0.4

Move to 0.0.5 usage first, then apply the table above:

| 0.0.4 usage | 0.0.5 replacement |
| --- | --- |
| `BlockContent::Parts(parts)` | `BlockContent::Message { role, parts }`; `BlockContent::text(role, text)` for one text part |
| Message role inferred from `BlockMeta::source` | The block's `role`; `source` is provenance only |
| Stored `{"shape":"parts",...}` blocks | `{"shape":"message","value":{"role":...,"parts":[...]}}`; no reader for the old form |
| An exhaustive `match` over `BlockContent` | Also handles `ToolChange` |
| `ModelRequest::tool_surface`, the protocol `render` tool argument | The frame's `ToolChange` blocks; read them with `current_tools` |
| A preparer that drops blocks it does not know | Keeps `ToolChange` blocks |
| `KernelGatewayConfig` methods | The three gateway aliases |
| Matching `anthropic` / `openai` error prefixes or the span field `provider` | The protocol name and the field `protocol`; prefer `ModelInvokeError::kind` |

## Upgrading from 0.0.3

Move to 0.0.4 usage first, then apply the tables above:

| 0.0.3 usage | 0.0.4 replacement |
| --- | --- |
| A pattern naming every field of a `TurnInterruption`, `RunEvent` or tool error variant | The same pattern ending in `..` |
| A test building one of those variants to compare with `assert_eq!` | `matches!` with the pattern |
| Comparing serialized tool output text that contains `"meta": null` or `"artifact": null` | Unset fields are left out; stored contexts written by 0.0.3 still load |

## Upgrading from 0.0.2

Move to 0.0.3 usage first, then apply the tables above. The changelog lists
every break with its migration; these are the ones most code meets:

| 0.0.2 usage | 0.0.3 replacement |
| --- | --- |
| Struct literals for options, outputs and requests | The type's constructor or `Default`, then `with_*` setters or field assignment |
| `Tool::execute(ctx, control)`, `DynamicToolSource::invoke(call, control)` | The same methods take the host's artifact store as a third argument |
| `RunControl` | `CallControl` |
| `ModelInvokeError::kind()` and matching on its message | The public `kind`, `status` and `code` fields |
| `ModelResponse` text and tool-call fields | An ordered list of `ModelItem` values |
| Stored tool results with `"Succeeded"`-style statuses | snake_case strings; rewrite stored context, no reader for the old form |
| A complete tool batch handed back on a late stop | The batch is committed; `uncommitted_tool_batch` is `None` |

## Upgrading from 0.0.1

Migrate these boundaries first, then apply the tables above:

| 0.0.1 usage | 0.0.2 replacement |
| --- | --- |
| `TurnContext`, snapshots and sealed turns | Editable `Context`; store the material your application retains |
| Implicit conversation history and `merged_frame` | Supply context explicitly; use `ContextPreparer` to edit retained material and select the request frame |
| Runner-owned model defaults and policies | `TurnRunOptions::new(model)` plus application-owned preparation and policy |
| Executor constructors and implicit tool lookup | `ToolExecutor::new(tools, options)`, then bind and process a fresh batch |
| `Session` and conversation storage | Application-owned session, work and persistence layers |
| Stored event history | Optional borrowed `RunEvent` observations; copy observations you need to keep |
| Previous context/session serialized data | Explicit application migration; no automatic compatibility reader |

Handle `TurnOutcome.result` and retain or dispose of returned context and any
uncommitted tool batch deliberately. An interrupted external tool may have an
unknown outcome; recreating context does not guarantee exactly-once execution.

The [full changelog](https://github.com/Preference-cmd/causa/blob/v0.1.1/CHANGELOG.md)
details the context, tool, control, conversion and protocol changes.
