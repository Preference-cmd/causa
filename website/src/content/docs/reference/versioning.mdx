## 0.1

**0.1.0** is the first minor release. Its API and the serialized form of
`Context` are those of 0.0.7; what changes is the promise. From 0.1.0, a
break of the public Rust API or of the stable serialized set (`Context` and
every type it contains) comes only in a minor release, `0.1` to `0.2`, with
its migration at the top of the release notes. Patch releases fix or add
without breaking, so `causa = "0.1"` picks them up. Adding an optional field
with a serde default is not a break. Other serializable types, such as model
output, request options, identifiers and error kinds, carry no promise.

On GitHub, a minor release is a regular release and a patch release between
minor releases is marked as a pre-release. Session management, history
policies and subagent orchestration belong to applications built on Causa.

In the earlier `0.0.x` series any release could break, and Cargo does not
upgrade `"0.0.7"` to `0.1.0` on its own.

## Upgrading from 0.0.7

Change the dependency to `causa = "0.1"`. No code changes are needed.

## Upgrading from 0.0.6

Change the dependency to `causa = "0.1"`. No code changes are needed: 0.0.7
only added the choice of the Chat output-limit field name and re-exported
`MediaPayload` and `MediaSource` from `causa-provider`.

## Upgrading from 0.0.5

Change the dependency to `causa = "0.1"`. The changelog lists every break
with its migration; 0.0.7 and 0.1.0 add none:

| 0.0.5 usage | 0.0.6 replacement |
| --- | --- |
| `MediaPayload::new(media_type, data_base64)` | `MediaPayload::inline(media_type, data_base64)` |
| Reading `payload.data_base64` | Matching `payload.source` (`MediaSource::Inline { data_base64 }`) |
| `with_max_inline_media_bytes(n)` | `with_max_inline_media_bytes(MediaKind::Image, n)`; documents have their own ceiling |
| Expecting a `[tool result media for call …]` user message on Responses | The media inside `function_call_output.output` |

## Upgrading from 0.0.4

Move to 0.0.5 usage first, then apply the table above:

| 0.0.4 usage | 0.0.5 replacement |
| --- | --- |
| `BlockContent::Parts(parts)` | `BlockContent::Message { role, parts }`; `BlockContent::text(role, text)` for one text part |
| Message role inferred from `BlockMeta::source` | The block's `role`; `source` is provenance only |
| Stored `{"shape":"parts",...}` blocks | `{"shape":"message","value":{"role":...,"parts":[...]}}`; no reader for the old form |
| An exhaustive `match` over `BlockContent` | Also handles `ToolChange` |
| `ModelRequest::tool_surface`, the protocol `render` tool argument | The frame's `ToolChange` blocks; read them with `current_tools` |
| A preparer that drops blocks it does not know | Keeps `ToolChange` blocks |
| `KernelGatewayConfig` methods | The three gateway aliases |
| Matching `anthropic` / `openai` error prefixes or the span field `provider` | The protocol name and the field `protocol`; prefer `ModelInvokeError::kind` |

## Upgrading from 0.0.3

Move to 0.0.4 usage first, then apply the tables above:

| 0.0.3 usage | 0.0.4 replacement |
| --- | --- |
| A pattern naming every field of a `TurnInterruption`, `RunEvent` or tool error variant | The same pattern ending in `..` |
| A test building one of those variants to compare with `assert_eq!` | `matches!` with the pattern |
| Comparing serialized tool output text that contains `"meta": null` or `"artifact": null` | Unset fields are left out; stored contexts written by 0.0.3 still load |

## Upgrading from 0.0.2

Move to 0.0.3 usage first, then apply the tables above. The changelog lists
every break with its migration; these are the ones most code meets:

| 0.0.2 usage | 0.0.3 replacement |
| --- | --- |
| Struct literals for options, outputs and requests | The type's constructor or `Default`, then `with_*` setters or field assignment |
| `Tool::execute(ctx, control)`, `DynamicToolSource::invoke(call, control)` | The same methods take the host's artifact store as a third argument |
| `RunControl` | `CallControl` |
| `ModelInvokeError::kind()` and matching on its message | The public `kind`, `status` and `code` fields |
| `ModelResponse` text and tool-call fields | An ordered list of `ModelItem` values |
| Stored tool results with `"Succeeded"`-style statuses | snake_case strings; rewrite stored context, no reader for the old form |
| A complete tool batch handed back on a late stop | The batch is committed; `uncommitted_tool_batch` is `None` |

## Upgrading from 0.0.1

Migrate these boundaries first, then apply the tables above:

| 0.0.1 usage | 0.0.2 replacement |
| --- | --- |
| `TurnContext`, snapshots and sealed turns | Editable `Context`; store the material your application retains |
| Implicit conversation history and `merged_frame` | Supply context explicitly; use `ContextPreparer` to edit retained material and select the request frame |
| Runner-owned model defaults and policies | `TurnRunOptions::new(model)` plus application-owned preparation and policy |
| Executor constructors and implicit tool lookup | `ToolExecutor::new(tools, options)`, then bind and process a fresh batch |
| `Session` and conversation storage | Application-owned session, work and persistence layers |
| Stored event history | Optional borrowed `RunEvent` observations; copy observations you need to keep |
| Previous context/session serialized data | Explicit application migration; no automatic compatibility reader |

Handle `TurnOutcome.result` and retain or dispose of returned context and any
uncommitted tool batch deliberately. An interrupted external tool may have an
unknown outcome; recreating context does not guarantee exactly-once execution.

The [getting-started example](/getting-started/) uses the new facade API. The
[full changelog](https://github.com/Preference-cmd/causa/blob/v0.1.0/CHANGELOG.md)
details the context, tool, control, conversion and protocol changes.
