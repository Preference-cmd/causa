---
title: Editing context material
description: Explicitly replace and append facts in a Context.
---

`Context` stores an ordered list of context blocks. When your application
decides that some material should be replaced, use the context edit API to
prepare the replacement and any new trailing blocks as one atomic change.
The kernel does not choose what to summarize or when to edit.

## Replace a range and append material

Create each new block with an ID supplied by your application. A changed block
needs a new ID; when you carry a block forward unchanged, clone or reuse the
existing `ContextBlock` so its ID, content, and metadata stay together.

```rust
use causa::{
    kernel::{BlockContent, BlockMeta, ContextBlock, ContentPart, TextPayload, Context},
    runtime::new_block_id,
};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut context = Context::new();
    for text in ["system note", "old detail one", "old detail two", "old detail three", "recent request"] {
        context.edit().append([ContextBlock::new(
            new_block_id(),
            BlockContent::Parts(vec![ContentPart::Text(TextPayload::new(text))]),
            BlockMeta::default(),
        )]).commit()?;
    }

    let summary = ContextBlock::new(
        new_block_id(),
        BlockContent::Parts(vec![ContentPart::Text(TextPayload::new(
            "The user prefers short answers and is building a Rust agent.",
        ))]),
        BlockMeta::default(),
    );
    let note = ContextBlock::new(
        new_block_id(),
        BlockContent::Parts(vec![ContentPart::Text(TextPayload::new(
            "The current request concerns context editing.",
        ))]),
        BlockMeta::default(),
    );

    context
        .edit()
        .replace(1..4, [summary])
        .append([note])
        .commit()?;

    println!("{} blocks", context.blocks().len());
    Ok(())
}
```

This example uses the runtime's `new_block_id()` convenience function. A
kernel-only application supplies its own IDs, for example by wrapping UUIDs in
`BlockId`.

Ranges use indexes from the original block sequence at the start of the edit;
earlier replacements do not shift later coordinates. Overlapping replacements
resolve in declaration order: a later one displaces the whole earlier
replacement, which does not reappear. An insertion exactly at a replacement's
right endpoint is adjacent and coexists; an insertion at its start or inside
it overlaps and is displaced by a later replacement. Appended blocks are added
after the replacement result, in append order.

An empty replacement deletes its range; an empty range inserts at that
position. Keep an owned copy before editing if you may need the original:
`context.blocks()[range].to_vec()` copies the selected blocks, including their
IDs and metadata. Editing does not mutate those copies. Causa does not retain
deleted blocks as hidden history, so save any material you need before
replacing or deleting it. A summary block is ordinary material; the caller selects which context to
retain and supply to a later run.

## Atomicity

Commit applies the whole edit or leaves the context unchanged. If validation
fails, the edit failure returns all submitted replacement and appended blocks,
including inputs from operations displaced by later overlapping edits. The
caller can inspect or reuse those values. A successful commit returns `()`.

A context remains editable after every run, including interrupted runs.
An empty edit is valid; there is no sealed lifecycle state.
Creating an edit builder does not change the context, and dropping an
uncommitted builder discards only that pending edit.

## Saving material

`Context` serializes as an object with one required field, `blocks`.
Loading validates block ID uniqueness. Empty Parts and partial tool material
are allowed; missing `blocks` and duplicate IDs are rejected. Generic import
and edit do not require a completed tool exchange. Runner result commits and
protocol rendering apply their own stricter rules at those boundaries.

`context.frame()` makes an independent, owned `ContextFrame` containing blocks.
A `ContextPreparer` can edit retained material and return a different frame for
one request. Preparation failure preserves edits already committed to context.
Neither value contains a turn ID or execution history.

Loading does not run tools or recover previously deleted blocks. Your application
owns summaries, history, session coordination and saved copies. Use `into_blocks()`
to transfer material without copying it.
