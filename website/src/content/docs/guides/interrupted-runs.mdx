## What it does

A run that does not complete returns `TurnResult::Interrupted` with a typed
cause. It still returns everything it committed: `TurnOutcome.context` holds
all material up to the stop. Nothing is rolled back and nothing is hidden.

The runner commits the model's tool calls before any tool runs. If the run
stops between that commit and the commit of the results, the context holds
calls without results, and `TurnOutcome.uncommitted_tool_batch` hands you
the batch. You answer what is still open, commit the results, and the
context is ready for the next run.

## When to reach for it

Whenever a run can stop while tools are involved: a stop button, a
deadline, a tool-call limit, or a processor that fails. Most other
interruptions, such as a failed model call, the round limit, a refusal or an
output cut off at the token limit, leave the context ready for another run
with no work from you.

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| A returned batch | Close it before the next run | The gateways refuse the next request: a call without a result cannot be rendered |
| Calls that never started | Answer them `Cancelled` or `Rejected` with a short reason | — |
| Calls that started | Keep the `unknown_outcome` the runner gave them | A failure status tells the model nothing happened, though the tool may have had its effect |
| Answer or remove | Answer. Remove the calls with a [context edit](/guides/edit-context/) only if you must | Provider-side material produced with a removed call, such as reasoning, is left without its counterpart |
| Long tool work | Return a handle at once and let the model ask for the status with a second tool | A stop during the work leaves a batch whose outcome is unknown |

How far the run got decides what the batch holds:

| Run stopped at | Cause | Batch |
|---|---|---|
| The tool-call limit | `MaxToolCalls` | every call pending, nothing started |
| A stop seen before tools were dispatched | `Cancelled`, `DeadlineExceeded` | every call pending, nothing started |
| A stop or failure while tools were running | `Cancelled`, `DeadlineExceeded`, `ToolProcessingFailed` | mixed: finished calls have their result, started calls have `unknown_outcome`, calls that never started are pending |
| A failure while validating or committing results | `ToolResultValidationFailed`, `ToolCommitFailed` | every call has a result, none is committed |

`ToolBatch::results()` are the calls that have a result, `calls()` the ones
still pending. A stop seen after every tool returned and every after
processor ran is not in this table: those results are committed and no batch
is returned.

## Common questions

**Why does nothing stay pending when I stop running tools?** The executor
starts every call of a batch at once, so a stop while tools run finds each
call finished or started. Calls stay pending when the run stops before
dispatch, at the tool-call limit, or in a before processor. The
[`interrupted_batch`](https://github.com/Preference-cmd/causa/blob/main/crates/causa-runtime/examples/interrupted_batch.rs)
example closes a batch left by the tool-call limit.

**What does `unknown_outcome` mean?** The tool started and its result was
not seen: it may have had its effect. Whether that effect has to be checked
before the conversation goes on is your application's decision.

**What about `UnknownToolOutcome`?** That interruption returns no batch. The
batch was committed in full, including the result marked `unknown_outcome`,
and the run stopped so that your application decides whether to continue.

**How quickly does a stop take effect?** At the tool's next yield point. A
tool that follows the [requirements on tools](/concepts/turns-and-batches/),
never blocking the thread and returning promptly once its control is
stopped, keeps the interruption prompt.

**Does the runner wait for background work?** No. It never polls or waits
for work a tool started. Your application owns the work behind a handle,
including stopping it.

**Does closing a batch make a tool run exactly once?** No. Closing records
what happened; it does not undo or repeat an external effect.

## It's working if

- The program prints `stopped: cancelled`, the two statuses and
  `not started: 0`, then `Results so far: Succeeded, UnknownOutcome.`
- In your application, the run after an interrupted one builds its request
  without `InvalidRequest`.
