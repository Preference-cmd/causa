## What it does

The context never holds media bytes. An image or a PDF is a `MediaRef`: a
media type and a reference, such as a content hash, that your application
chose. The bytes stay in your asset store. When a gateway builds a request,
it asks your `MediaResolver` for the payload of each reference and puts it
on the wire, inline or as a URL.

Media enters the context in two places: as a part of a user message, and
attached to a tool result. A tool stores its bytes through the
`ArtifactStore` it is given, and returns the reference with its result.

What each protocol can carry:

| | Anthropic Messages | Chat Completions | Responses |
|---|---|---|---|
| Image in a user message | yes | yes | yes |
| Image from a tool | in the tool result | in a user message after the tool message | in the function call output |
| PDF | yes, as a document | no | no |

Anything a protocol cannot carry is sent as a line of text instead, such as
`[media: application/pdf report.pdf sha256-82952bb9e32344c6]`, and the request
still goes out.

## When to reach for it

When users send images or documents, or a tool produces them: a chart, a
screenshot, a page of a scanned file.

## Before you start

The program hashes and encodes the bytes itself:

```bash
cargo add sha2@0.10 base64@0.22
```

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| The reference | A hash of the content | One reference could come to mean other bytes; see the next row |
| What a reference resolves to | The same payload for as long as any context holding it is sent | A changed answer rewrites a message the provider already saw: the prompt cache is lost from there on, and Anthropic refuses requests with thinking blocks after it |
| Where the resolver reads from | Memory only; load the assets of a conversation before its run | The resolver is synchronous and is called for every reference in every request |
| A tool's bytes | Set `ToolExecutorOptions::artifact_store`, and persist through the `store` argument | `store` is `None`; MCP images become a line of text |
| Large files | Keep each inline payload under 5 MiB, or raise the limit with `with_max_inline_media_bytes` | A larger payload is sent as the text placeholder |
| Files the provider can download | Return `MediaPayload::url`, with an address that serves the bytes directly, without a redirect | — |
| Old media in a long conversation | Return `None` for references you no longer want to send; they become text placeholders | Every image in the context is sent with every request |
| PDFs on Chat or Responses | Extract the text yourself and send it as text | The model sees only the placeholder line |

## Common questions

**What does the stored context hold?** The media type, the reference and the
name, nothing else. Saving the context does not save the bytes: keep your
asset store alongside it.

**What happens if the resolver has no answer?** The reference is sent as the
text placeholder. A missing asset is not an error, which is what lets you
stop sending old media.

**Can the model return images?** Not through the built-in gateways: they
read text, tool calls and reasoning from the model's answer.

**Does the gateway download URLs?** No. The provider fetches them, on every
request that carries them; a failed fetch comes back as the provider's
error.

**What about media in assistant or system messages?** Only user messages and
tool results carry media. In any other position, the reference is sent as
the placeholder.

## It's working if

- The program prints an `image` inside Anthropic's `tool_result` and a
  `document` in its last user message, an `image_url` in a Chat user
  message, and placeholder lines for the PDF on Chat and Responses.
- In your application, the provider describes the image, and the saved
  context holds references, never base64.
