## What it does

All three gateways stream. A stream yields deltas, pieces of text,
reasoning, tool calls and usage, and ends with `Done`, which carries the
complete output. Deltas are for display; the complete output is what the
context records.

There are two ways to read a stream. `TurnRunner::run_streaming` runs the
turn as `run` does, tools included, and passes each delta to your observer.
`ModelGateway::stream` gives you the stream itself, for an application that
runs its own loop.

## When to reach for it

When a person watches the answer being written. A batch job or a server
that returns only the final answer has no use for deltas: call `run`.

## Before you start

Reading a stream directly needs `StreamExt`:

```bash
cargo add futures-util@0.3
```

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| Runner or direct | `run_streaming` with an observer when Causa runs the tools; `gateway.stream()` when your code runs the loop | — |
| What to display at the end | Replace the streamed text with the final output | The display can differ from the stored answer: a provider's final snapshot can differ from its deltas |
| Which tool calls to act on | The ones in `Done`, or committed by the runner | Arguments in a `ToolCallDelta` can be incomplete JSON, and a call cut off by the token limit is in the deltas but not in `Done` |
| Usage | Keep the last `Usage` delta | Usage deltas are snapshots: summing them counts tokens twice |
| A slow display | Send the deltas to a channel from the observer | The observer is synchronous: the stream waits for it |
| Retries | Wrap the gateway in `RetryingGateway` | A failed stream ends the run. Even with retries, a stream is never retried once a delta has arrived |
| Size limits | `with_stream_limits` on the gateway | The default limits apply; a stream over one fails as `Undecodable`, never as a cut-off success |
| Your own HTTP client | Disable retries and redirects on it | Its own policies apply; the default client has both off |

What each protocol streams, and when its stream is complete:

| Protocol | Deltas | Complete when |
|---|---|---|
| OpenAI Chat Completions | Text and function-call pieces of one choice; usage at the end | A valid finish reason, then `[DONE]` |
| OpenAI Responses | Text, reasoning summary and function arguments | A complete terminal response; incomplete and failed responses are reported as such |
| Anthropic Messages | Text, thinking and its signature, function input, cumulative usage | Every content block closed, then a valid `message_stop` |

## Common questions

**What does the runner commit from a stream?** Only the complete output in
`Done`, after it reports it as `RunEvent::ModelOutput`. The observer never
sees `Done` or `Error` as deltas, and no tool runs from a delta. If a round
stops mid-stream, nothing of that round is committed; earlier rounds stay in
the context.

**What ends a stream with an error?** A cut-off stream, a malformed event,
invalid tool arguments and an error from the provider. None of them becomes
a partial success. An Anthropic content-block delta of a type the decoder
does not know fails the stream as `Undecodable` rather than being dropped,
since the block would otherwise be stored incomplete. Unknown event types
are ignored.

**What if the endpoint answers with JSON instead of a stream?** A streaming
answer must be `text/event-stream`. A JSON error body fails the call with the
provider's message and code; any other body fails as `Undecodable`. There is
no fallback request.

**Is reasoning streamed?** When the provider sends it in a supported event,
yes. It is kept whole in the output, as the provider's own sealed format, and
sent back to the same protocol in later requests. On Anthropic, thinking is
turned on with a `thinking` object in `GenerationOptions::extra_body`;
`reasoning_effort` only sets `output_config.effort`.

**What does cancelling do?** `CallControl` applies while the stream is
opened and while it is read, through the runner or not. It is checked between
reads and between events; parsing one event is not interrupted. Dropping the
stream frees the connection and the parser. That does not prove the provider
stopped generating.

**Does the gateway read ahead?** No. It reads when you ask for the next
delta, with no background task and no unbounded buffer. After `Done` it
stops reading.

**What is not supported?** Audio and image output streams, tools hosted by
the provider, and more than one choice in Chat Completions.

## It's working if

- The program prints `[Hel][lo ][there.]`, then `runner: Hello there.`, then
  the direct pieces and `direct: Hello there.`.
- In your application, text appears as it is generated, and the context
  after the run holds the same answer as the final output.
