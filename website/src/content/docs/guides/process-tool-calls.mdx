## What it does

The calls a model makes in one round form a batch. Before the executor runs
them, the batch passes through your *before* processors, in order; after
every call has a result, it passes through your *after* processors. A
processor is a `ToolBatchProcessor`: an async function that gets the batch
mutably.

The same processors see every call, whether the tool is yours or comes from
an MCP server.

## When to reach for it

- Ask a person before a call runs.
- Ask only about tools that change something, and follow the permission
  mode the user picked.
- Refuse calls by a rule: a path outside a directory, a command not on a
  list.
- Change arguments, such as capping a limit, and tell the model why.
- Shorten or redact results before they enter the context.
- Record results in the order the model declared the calls.

## Before you start

The program waits for its approver over a channel, which needs the tokio
`sync` feature:

```bash
cargo add tokio@1 --features macros,rt,sync
```

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| A call that must not run | In a before processor, resolve it with a `Rejected` result | The tool runs |
| Arguments that need changing | In a before processor, edit `input_mut()` and explain with `push_note` | The tool gets the model's arguments |
| Waiting for a person | Await the answer in the before processor; the whole batch waits | — |
| Which calls to ask about | Read `ctx.hints(name)`: what the tool declares about itself, such as `read_only` | The processor cannot tell a read from a write |
| State that differs between runs, such as a permission mode | Pass it with `TurnRunOptions::with_processor_data` and read it with `ctx.data::<T>()` | The processor has only what it was built with, shared by every run of the executor |
| The approver goes away | Treat a missing answer as a no | — |
| Large or sensitive output | In an after processor, edit `output_mut()` | The whole output enters the context |
| The order of results | Sort `results_mut()` by `ctx.declaration_order` in an after processor | Results are recorded as they finished: calls resolved by a before processor first, then the rest in completion order |

What each phase may change is checked after every processor:

| | Before | After |
|---|---|---|
| Edit the arguments of a pending call | yes | no |
| Resolve a call with a result | yes | no |
| Edit outputs and media | yes, of the calls it resolved | yes |
| Add notes | yes | yes |
| Reorder results | yes | yes |
| Remove notes, change a status, add or drop calls | no | no |

A processor that breaks one of these rules, or returns a `ProcessorError`
because it cannot finish, stops the run with `ToolProcessingFailed`; the
batch is handed back in the outcome.

## Ask only when it matters

A processor can also read what each bound tool declares about itself, and a
value your application passes for the run. Together they let one processor
follow a permission mode the user picks, such as read-only or full access.

A tool declares its effects in `hints`. A tool that declares nothing has
every hint unset:

MCP tools get the hints their server's annotations declare; see [Connect MCP
servers](/guides/connect-mcp-servers/).

The modes are your own type; Causa has none. Put a shared handle to the
current mode in the run's options. Causa hands the same value to every
processor of the run without copying it, so a switch the user makes during
the run is seen by the next decision:

Hints are the tool's own claim, and nothing checks them. Trust them as far
as you trust the tool: your own tools, fully; an MCP server's, only as far
as you trust the server.

## Common questions

**Does a rejected call end the run?** No. A rejection is a result like any
other: the model reads it in the next round and can answer without the tool.

**What does the model see from a note?** Notes render with the result they
belong to. A note added before the call runs is placed ahead of the notes
the tool returns.

**What happens if the run is cancelled while a before processor waits?** The
executor stops waiting, and the run returns `Interrupted` with the cause
`Cancelled`. No call of the batch has run, and the batch is handed back in
the outcome.

**Can a processor see earlier rounds?** It gets the batch and a
`ProcessorContext`: the turn, the round, the declaration order, the run's
`CallControl`, the bound tools with their hints, and the run's data if you
set any. Anything else it needs, such as a session's earlier approvals, it
keeps itself or reads from that data.

**Does a change in hints change what the model sees?** No. Hints never reach
the model or the context. A server that changes only its annotations
records no tool change, and the provider's prompt cache still matches.

**Should approval live in the tool instead?** Keep it in a processor. Then
one rule covers every tool, MCP tools included, and the tools stay free of
policy.

## It's working if

- The program prints the two questions, the `Succeeded` result, the
  `Rejected` result, and the model's answer, in that order.
- In your application, a refused call has a `Rejected` result in the context
  and its tool never ran.
