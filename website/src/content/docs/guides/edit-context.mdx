## What it does

`context.edit()` starts an edit: replacements of ranges of blocks, and
blocks to append at the end. `commit()` applies all of it, or none of it
and hands every submitted block back. Causa does not decide what to
summarize, drop or keep, or when: the edit API only carries out what your
application decided.

## When to reach for it

Between runs, to replace old turns with a summary, drop tool output nobody
needs, or correct a message. For a change to one request only, leaving the
context as it is, [prepare the request](/guides/prepare-each-request/)
instead.

## Before you start

The edit API is in the kernel, which every feature selection includes. This
guide makes ids with the runner's `new_block_id()`; with
`--no-default-features`, wrap your own UUIDs in `BlockId::new`.

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| Ids of new and changed blocks | Give every new block, and every changed one, a new id | Reusing an id for other content refuses the edit with `BlockIdentityMismatch` |
| Blocks you keep | Leave them in place, or clone the whole `ContextBlock` to move it | — |
| What the edit removes | Copy it first: `context.blocks()[range].to_vec()` | It is gone; the context keeps no history |
| Tool calls and their results | Replace or remove them together | The gateway refuses the next request with `InvalidRequest` |
| Tool changes | Leave `ToolChange` blocks in place | The runner records the tools again before the next request |
| Model output | Replace whole turns, not parts of one | A rewritten assistant block is a new block: it is sent from its content alone, without the provider fields or reasoning the original carried |

## Common questions

**How do I delete or insert?** An empty replacement deletes its range; a
replacement of an empty range, such as `2..2`, inserts at that position.

**What if two replacements overlap?** They resolve in the order you declared
them: a later one displaces the whole earlier one, which does not come back.
An insertion at the right end of a replacement is adjacent to it and both
apply; an insertion at its start or inside it overlaps and is displaced by a
later replacement. Appended blocks go after the result of all replacements,
in the order given.

**Do earlier replacements shift later ranges?** No. Every range uses the
indexes the blocks had when the edit started.

**What does a failed edit hand back?** Every replacement and appended block
you submitted, including those displaced by a later overlapping
replacement, in `EditFailure`.

**Can I edit after an interrupted run?** Yes. A context has no closed
state: it can be edited after every run, an empty edit is valid, and
dropping an edit without committing it discards only that edit.

**Can I make tool calls without results, or empty messages?** The edit API
allows both; it only checks ids. The runner and the gateways check their
own rules when they use the context, so a call without a result has to be
answered before the next request. [Handle interrupted
runs](/guides/interrupted-runs/) shows how.

**How do I take the blocks out without copying them?**
`context.into_blocks()` hands over the vector.

## It's working if

- The program prints four blocks with the summary in second place, then
  `3 blocks replaced`, then a refused edit with 4 blocks before and after.
- In your application, a failed `commit()` leaves `context.blocks()`
  exactly as it was.
