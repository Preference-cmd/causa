## What it does

`McpToolSource` is an MCP client. It connects to one server, lists the
server's tools, and calls them when the model asks. You register it with the
executor, and from then on the model sees the server's tools next to the
tools you wrote, and the runner treats them the same way.

Each tool is renamed `mcp_{server_id}_{tool}`, with the `server_id` you
choose when you connect, so two servers can both offer a `search` tool.

## When to reach for it

Use it for tools that already exist as an MCP server: a server you start as
a child process (stdio), or a remote one (Streamable HTTP). For a function
of your own application, [write a tool](/guides/write-a-tool/) instead: it
needs no server and no extra process.

## Before you start

The MCP client is not in the default features. Add it with:

```bash
cargo add causa --features extension-mcp
cargo add tokio@1 --features macros,rt,process
```

For the remote case, you need the server's URL and, if it asks for one, a
static token. OAuth sign-in is not supported.

## The decisions

| Decision | What to do | What happens if you don't |
|---|---|---|
| The `server_id` | A short name of letters, digits, `_` and `-`, unique per executor | `register_dynamic` returns `DuplicateSource` for a second source with the same id |
| A server tool with the name of one of yours | Choose a `server_id` that keeps the names apart | Listing fails with `DuplicateTool` and the run stops before calling the model |
| Approval | Check calls in a before processor; it sees MCP calls and your own calls alike | The model can call every tool the server offers |
| A call deadline (`ToolExecutorOptions::call_timeout`) | Set it high enough for the server's slowest tool | A call past it is recorded as an unknown outcome and the run stops: the server may have done the work |
| Images, audio and files in results | Set `ToolExecutorOptions::artifact_store`; they are saved there and the result refers to them | Each becomes a line of text such as `[image: image/png — no media store available]` |
| Shutting down | Unregister the source and call `close` | The session ends when the last reference to the source is dropped, without a shutdown handshake |

## Common questions

**When does the executor ask the server for its tools?** The first time the
runner binds the executor, and again after the server sends
`tools/list_changed`. Between those, it reuses the list, across rounds and
across turns.

**What happens if the server is gone?** If it is gone when the tools are
listed, the run stops with `ToolCatalogFailed`, before the model is called.
If it goes away later, each call to it is recorded as `Failed` and the model
reads the error.

**What does the model see when an MCP tool fails?** A tool that reports an
error (`isError` in MCP) is recorded as `Failed`, with the server's text as
the output. The run continues.

**What goes into the result?** The text the server returns, joined into one
string, or its structured content when the tool returns some.

**Do MCP calls run in parallel with my own tools?** Yes. The calls of one
batch run concurrently, whichever source they come from.

**Is a server's output safe to give the model?** Treat it as untrusted
input: it can contain instructions meant to steer the model. Keep approval
for tools with effects in a before processor.

## It's working if

- The program prints `tool: mcp_notes_read_note`, then the result and the
  model's answer.
- With a real server, it prints one `tool: mcp_local_…` line for each tool
  the server offers.
